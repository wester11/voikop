# Безопасное переключение и возврат транспорта

## Граница автоматизации

Локальный установщик Remnawave не имеет настроенного авторизованного доступа к панели. Он не назначает Config Profile, не меняет Node/Host/Squad и не подменяет файлы runtime внутри контейнера. Поэтому в интерфейсе доступны подготовка кандидата, план переключения и инструкция возврата; фактическая активация и откат выполняются в Remnawave Panel.

Папки `/var/lib/remna-node-transport-manager/candidates/*` — только локальные шаблоны со статусом `PREPARED ONLY`. Их наличие не означает, что профиль создан или назначен. Каталоги создаются уникальными и не перезаписывают предыдущие.

## До canary

1. Зафиксируйте Node, действующий Config Profile и включённые inbound.
2. Экспортируйте исходный профиль без изменения его outbound, routing, DNS, balancer и других общих параметров.
3. Составьте список Hosts, Squads и пользователей, которые зависят от профиля/inbound.
4. Проверьте, что отдельный кандидат сохраняет действующие inbound. Не удаляйте текущий транспорт при добавлении тестового.
5. Проверьте Host/Template и фактически выдаваемую клиенту конфигурацию; не считайте валидный JSON snippet тестом выдачи.
6. Получите согласование перед назначением нового профиля или изменением единственного inbound на `443`.

Если текущий и новый inbound претендуют на тот же TCP socket `443`, не рассчитывайте на одновременный запуск двух inbound. Используйте отдельную тестовую Node или отдельно согласованный свободный endpoint; не открывайте новый порт без согласования.

## Canary-переключение

1. Используйте одну согласованную тестовую Node/Host и разрешённое клиентское подключение.
2. Сохраните копию текущего назначения профиля и набора enabled inbound.
3. Создайте отдельный Config Profile вручную. Перенесите в него нужные действующие inbound и сохраните общий routing без изменений.
4. Сначала проверьте новый профиль на тестовом Host и получите клиентскую ссылку/JSON из панели.
5. После явного разрешения назначьте профиль только canary Node.
6. Проверяйте отдельно: Node Connected, нужный listener, TLS/REALITY handshake, VLESS authentication, передачу данных, DNS и маршрутизацию. `rw-core running` и HTTPS сайта не доказывают VPN.
7. Не меняйте другие Nodes, Hosts, Squads, пользователей или каскадные маршруты в ходе canary.

## Возврат

1. В Remnawave верните canary Node к сохранённому Config Profile.
2. Верните исходный набор enabled inbound.
3. Если во время canary менялся Host/Template/Mapper, восстановите его экспортированную копию.
4. Проверьте Connected, исходный inbound и разрешённое клиентское подключение.
5. Не удаляйте старый профиль до проверки зависимостей и возврата всех пользователей.

Переключение единственного сервиса на одном IP и TCP/443 может оборвать действующие соединения. Этот документ не обещает бесшовного переключения. Не выполняйте `docker compose up/down`, ручную замену runtime config или restart Remnanode ради возврата транспорта без отдельного согласования.

## Результат текущего релиза

Автоматическая Panel API активация/rollback и canary-тест здесь не реализованы и не проверены. Для внешнего release gate требуется отдельный изолированный Remnawave test instance либо согласованный тестовый Node с разрешённым клиентом.
